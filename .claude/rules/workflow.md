# Implementation workflow

1. Read the project brain and routed contracts.
2. Refresh the exact GitHub issue, open pull requests, and current branch before editing.
3. Record whether the work is new code, tracker cleanup, already complete, or a research experiment.
4. Preserve existing user changes and the founder-tested proof.
5. Implement the smallest coherent slice with tests and content-free diagnostics.
6. Self-audit privacy, cancellation, failure fallback, and public-repository safety.
7. Run the canonical validation command plus any task-specific native Windows checks.
8. For user-facing behavior, complete the actual Windows user path or state the exact unobserved condition.
9. Commit, push, and open or update the pull request. Never leave finished work only on one machine.
10. Do not merge unless Saurabh explicitly asks for that exact merge.

Use GitHub Issues for persistent follow-up. Every new issue needs a priority and type. Review findings must
include the exact proposed fix. Experimental work gets one smoke run and one full benchmark before a stop
and decision unless it clearly improves the target without meaningful regressions.
